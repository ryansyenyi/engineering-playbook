JWT

A signed, self-contained set of claims a recipient can verify without calling back to the issuer. That stateless property is the entire reason to reach for a JWT — and the source of everything hard about revoking one.

When to use

Use a JWT as an access token for service-to-service calls or API access where the verifying party should not need a shared session store. Keep lifetimes short: the token is a bearer credential you cannot take back before it expires.

For browser-facing applications, prefer a session cookie. The comparison is scored in JWT vs session cookies.

Revocation A JWT is valid until it expires. If you find yourself building a denylist to log tokens out, you have rebuilt the session store you were avoiding — with worse ergonomics. Shorten the lifetime instead.

Implementation guidance

Follow RFC 8725 best current practices. Pin the algorithm at the verifier; never accept the token's own alg header as authority.

# verifier configuration — the four checks that matter
algorithms: ["EdDSA"]          # pinned, never "none"
issuer:     "https://auth.internal"
audience:   "orders-api"          # reject tokens minted for another service
max_ttl:    300                   # seconds — short by default
  • Validate iss, aud, exp, and nbf on every request — a missing check is a bypass.
  • Sign with an asymmetric key (EdDSA or ES256) so services verify without holding a signing secret.
  • Never put a JWT in localStorage — XSS exposure is the top real-world failure.

Verification

Before shipping, prove the verifier rejects: a token signed with none, an expired token, a wrong-audience token, and a token signed by a rotated-out key. Four requests, four 401s.
