JWT vs session cookies

The decision is about revocation, not about tokens. A JWT is a bearer credential you cannot take back before it expires; a session identifier is a lookup you can delete. Everything else follows from that.

Scored comparison

CriterionJWT (stateless)Session cookie (server state)
RevocationHard — valid until expiryEasy — delete the session
Horizontal scaleNo shared store neededNeeds shared session store
Payload sizeGrows with claimsOpaque identifier only
XSS exposureHigh if stored in localStorageLow with HttpOnly
Logout semanticsNeeds a denylistImmediate
Best fitShort-lived service-to-serviceBrowser-facing applications
Verdict Browser-facing: session cookies. Service-to-service with short lifetimes: JWT. If you need both, keep them separate — do not make one token serve two trust models.

Tradeoffs

Statelessness buys horizontal scale and costs you immediate logout. Most applications that adopt JWTs then rebuild session state as a denylist — which is the state they were avoiding, with worse ergonomics.

Migration path

Moving an existing JWT-in-browser deployment to cookies, in order:

Shorten the access-token lifetime

Get exposure down before touching architecture. 5 minutes is a defensible ceiling.

Move the token out of localStorage

Serve it as an HttpOnly, Secure, SameSite=Lax cookie. XSS can no longer read it.

Introduce the session store

Swap the JWT payload for an opaque identifier; claims move server-side.

Delete the denylist

Logout is now a session delete. The workaround infrastructure goes away.
